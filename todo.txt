pulls it straight out of the sibling repos, so two changes made during the sweep
are already in this build path with no action taken here: romwbw_emu bf03758
fixed HBF_VDAKST (it set only E, never the status byte in A, so a guest polling

this project compiles.


emu_io_common.cc is the one core file this port does not share
--------------------------------------------------------------

- z80cpmw.vcxproj references emu_io_common.cc nowhere, and emu_io_windows.cpp
carries its own copies of the twelve functions it holds: emu_disk_{open,close,
read,write,flush,flush_all,size}, emu_file_{load,load_to_mem,save} and
emu_get_time.  The split is deliberate - the Windows versions use Win32 handles
rather than FILE* - but the consequence is that a fix landing upstream never
reaches here and nothing reports the drift.  Two have landed since: ce9268f
hardened the shared file I/O, and 573c7cc removed fseeko/ftello, which are POSIX
and which Windows does not have.  Worth one pass diffing the twelve against
romwbw_emu/src/emu_io_common.cc to see whether either applies, and worth a
comment at the top of emu_io_windows.cpp saying it is the Windows half of that
file, so the next person looks.


The console bugs cpmemu found and cannot fix from POSIX
-------------------------------------------------------

These are cpmemu's, not this repo's, but they are Windows console bugs and
whoever has the machine can do both at once.  cpmemu/todo.txt has the full
measurements.

- a character whose first byte is 0xE0 is still taken for a special-key prefix
when another byte follows it.  Measured on console code page 437: alpha (U+03B1)
alone reaches _getch() as E0 with _kbhit() false and the guest gets it; alpha
immediately followed by A gives E0 41, the 41 is consumed as a scan code, no
table entry matches, and the guest gets neither character.  Code page 65001
turns the race into a certainty - U+0E01 encodes as E0 B8 81 and _getch() hands
those back one byte at a time.  The fix is to stop using _getch() and read
INPUT_RECORDs directly, which removes the guess rather than narrowing it.  That
is a rewrite of the input path, not a patch to it.

- ctrl+break leaves the console in raw mode.  Clearing ENABLE_PROCESSED_INPUT
suppresses ^C but not ctrl+break, and the default handler ends the process
without running atexit, so disable_raw_mode() never runs.  Measured: the child
exits 0xC000013A and the console mode stays at 0x1A0 instead of returning to
0x1F7, which leaves the shell with no echo.  A SetConsoleCtrlHandler that
restores the mode and exits would fix it.  The POSIX half of the same problem is
done - cpmemu's os/linux/platform.cc catches SIGHUP, SIGINT, SIGQUIT, SIGTERM,
SIGSEGV, SIGBUS and SIGABRT, restores and re-raises, and seven cases in
tests/pty_console.cc hold it to that.

- nobody has pressed the keys.  cpmemu's tests/win_console.cc writes
INPUT_RECORDs into the console input buffer with WriteConsoleInput; it is
faithful from the console inward and steps past the terminal program itself.  If
Windows Terminal binds ctrl+left for its own use the test still passes and the
user still loses the key.  The harness has a --manual mode that runs a hex echo
to type at: one pass in Windows Terminal, one in a legacy conhost window.  Its
POSIX twin wants the same treatment in Terminal.app and iTerm2, which is also
not done.

- cpmemu's test suite skips two cases for want of this platform: "windows
cross-compile (x86_64-w64-mingw32-g++ not on PATH)" and "windows console (needs
a real Windows console)".  Running tests/run_tests.sh on Windows turns 59
passed / 4 skipped into something better.

Terminal residue - why this repo's own row 13 is not a tick
------------------------------------------------------------

- FEATURE_PARITY.md item 13 marks this repo partial for two reasons, both still
true: there is no per-cell attribute beyond the packed CGA byte, and clear()
resets the attribute and the escape state, which ESC[2J alone should not do.
The 73-check conformance suite described in CHANGELOG [1.0.20] is not committed
to this repository, which is worth fixing at the same time - it is the only
thing that would catch a regression in any of this.

- no action needed, recorded so it is not re-investigated: ioscpm gained F1-F12
in its build 51, using this repo's exact key names and the exact VT220 sequences
from z80cpmw/Keymap.h.  That was the last reason key maps were not portable
between the two ports.  ioscpm also gained ICH/DCH/ECH/SU/SD and DECAWM/DECTCEM
in the same build, which this repo has had since 1.0.20.
