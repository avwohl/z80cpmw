- 1.0.25 makes a superseded disk image visible and does not yet make it go away.
Two pieces are missing, and CHANGELOG [1.0.25] has the design behind both:

  * Nothing calls downloadDisk() for a DiskRefreshPlan::RefreshNow.  The caller
  has to be the UI rather than DiskCatalog, because isMounted is MainWindow's
  fact - replacing a file the running machine holds in a slot undoes itself on
  the next flush.  Wants an Update button beside Download and Delete.

    THE URL SWITCH HAS LANDED, SO THIS IS NOW LIVE RATHER THAN HYPOTHETICAL.
    The v0 catalog gives hd1k_combo the hash 0ca4ec60... where v1.4.12 gives it
    89b8ae1a..., which would have made every migrated combo read
    SupersededPristine - action() turns that into RefreshAutomatically and
    plan() into RefreshNow - had the equivalence below not been recorded first.
    Nothing calls either:
    grepping the tree, action, plan, RefreshNow, RefreshAutomatically and
    allowsUserRequestedUpdate appear only in DiskLedger and in
    tests\test_diskledger.cpp.  That wiring is what an Update button would
    supply.

    DECIDED 2026-09-05, AND THE VERDICT IS NO LONGER SUPERSEDED.  The two images
    were compared byte for byte: both 51,380,224 bytes, slices 1-5 identical,
    slice 0's directory listing the same 94 files, and all 94 extracting
    byte-identical - r8.com and w8.com included.  The 2,342 bytes that differ are
    CP/M slack between those files.  diskv0::isEquivalentPriorImage records that
    one pair and DiskLedger::freshness now returns Current for it, so the
    Settings column no longer says "Update available" and an Update button, when
    one is wired, will not offer 49 MB for nothing.  It is keyed on provenance:
    a download records the catalog it was fetched against, so only the migration
    can produce it, and it stops applying once this machine fetches the canonical
    image.  romwbw_disks docs/FINDINGS.md section 10 has the byte ranges.

  * A user who never opens Settings is never told.
  downloadAndStartWithDefaults() now fetches the catalog when it has to download
  something, but not when both default images are already there - which is the
  case this item is about - so a boot notice still means a network fetch at
  every launch: a real behaviour change, to decide rather than assume.

  MainWindow.cpp and SettingsDialogWx.cpp are in no suite and cannot be, so both
  are verified by driving the built app.  See WIP.md.

- The catalog index is switchable, and its downloads are still not isolated.
catalogv0::indexScope() computes the per-index suffix, is tested, and HAS NO
CALLER: every catalog reads and writes one data folder, so two catalogs
publishing an image under one name share one file.
  What ioscpm does instead is give each index its own Disks folder and its own
per-release settings keys, so a visit to a test catalog cannot touch the library
the machine already has, and coming back finds it untouched.  Its build 69 is
titled "point the catalog index somewhere else, and take its storage with it".
  THE OBSTACLE IS NOT THE SUFFIX, it is where to apply it.  The catalog's own
download directory does have a single choke point - DiskCatalog::getDownloadDirectory(),
which m_downloadDir reaches nowhere else - but %LOCALAPPDATA%\z80cpmw\data is
also computed in emu_io_windows.cpp's getDataFolder(), and THAT one is the R8/W8
host-file transfer folder as well as the place disks are read from.  Scoping the
catalog's half alone would have the emulator read a folder the catalog does not
write; scoping both would move the user's file-transfer folder, which is not
catalog data and is not this feature's to move.  It also needs a migration:
existing installs have their images in the unscoped folder under absolute paths
stored in the config.
  WHAT HAS BEEN DONE INSTEAD is to make the sharing safe and visible, which is
not the same thing and does not close this item:
    * a download is fetched under <name>.new and moved onto the real name only
      after its sha256 matches, so a cancelled, failed or corrupt transfer can no
      longer destroy the file that was there.  It used to write straight to the
      real path and DeleteFileA it on every failure arm.
    * replacing an image whose bytes have changed since it was written asks
      first and says what it costs; one that is merely superseded asks too.  The
      Download button used to refuse both, because isDiskDownloaded() is a size
      test and two catalogs' images are usually the same size.
    * Start reports a mounted image the catalog in hand does not vouch for, and
      boots it anyway.  DiskLedger::mountedCopyIsNotTheCatalogImage is the policy
      and is in a suite; it is deliberately silent for NeedsMeasurement and
      Unverifiable, so a launch that never fetched says nothing rather than
      accusing every disk.
    * the Settings note says the folder is shared - and is now readable, which it
      was not: it was drawn on one unwrapped line and clipped after about seventy
      characters, so the whole warning and the "In use:" URL were off the page.
  "Nothing wrong is ever booted - a mismatched image fails its sha256 and is
re-fetched" was in this item and in Config.h, and it was FALSE: every diskhash::
call is in DiskCatalog.cpp, and the mount path never hashes.  Nothing re-fetches
an image already on disk except a user clicking Download.  The notice above is
what stands in for it.
