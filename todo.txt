- two Windows console bugs in cpmemu/src/os/windows/platform.cc.  Not this
repo's code - z80cpmw compiles none of it - but whoever has the machine can take
them at the same time; cpmemu/todo.txt has the measurements.  (a) read_one_key()
takes a 0x00/0xE0 byte from _getch() as a special-key prefix and uses _kbhit()
as the tie-breaker, which code page 437 loses intermittently and code page 65001
loses always; the fix is to read INPUT_RECORDs with ReadConsoleInputW, which
removes the guess rather than narrowing it, and it forces five secondary changes
(key-down filter, repeat-count expansion, UTF-16-to-bytes conversion, re-keying
extended_keys[] from CRT scan codes to VK plus a ctrl flag, and widening the
two-slot queue).  (b) ctrl+break leaves the console in raw mode, because the
default handler ends the process without running atexit; one
SetConsoleCtrlHandler beside the existing atexit(disable_raw_mode) fixes it,
mirroring os/linux/platform.cc's install loop.

- cpmemu's tests/win_console.cc cannot inject a non-ASCII character -
inject_spec()'s single-character branch goes through VkKeyScanA and casts one
byte to WCHAR - and it never calls GenerateConsoleCtrlEvent, so neither bug
above has a regression test.  Both are small additions to the harness.

- cpmemu's tests/run_tests.sh skips two cases for want of this platform -
"windows cross-compile" and "windows console".  Running it here turns 59
passed / 4 skipped into a real result.

- nobody has pressed the keys.  cpmemu's win_console.cc writes INPUT_RECORDs
straight into the console input buffer, so it is faithful from the console
inward and steps past the terminal program itself: if Windows Terminal binds
ctrl+left for its own use the test still passes and the user still loses the
key.  The harness has a --manual mode - one pass in Windows Terminal, one in a
legacy conhost window.  Its POSIX twin wants the same in Terminal.app and
iTerm2, which is also not done.

The disk images are behind the core
------------------------------------

READ romwbw_emu/docs/RELEASE_ORDER_2026-08-25.md BEFORE PUBLISHING ANYTHING
HERE.  Refreshing the images is what arms a data-destruction bug in ioscpm, so
the port fixes go first and the images second, and the two rules that document
states plainly are (a) never attach refreshed images to the existing v1.4.5 tag,
because every port pins that tag in its binary and overwriting it reaches
installed apps with no update, and (b) never publish an image whose w8.com lacks
the 0xE9 capability probe.  z80cpmw is step 3 of that plan and is not a safety
blocker - the code side of it is done as of this round.

- the bundled hd1k images still carry the pre-98eb6a1 w8.com, so W8 cannot take
a host path however capable the Windows backend is, and cannot ask where its
export really went either.  Measured: bin\Release\disks\hd1k_combo.img holds
"Usage: W8 <cpmname>" where romwbw_emu/disks/hd1k_combo.img now holds
"Usage: W8 <cpmname> [hostpath]" - and the two are different lineages, not just
different vintages, because the local copy came down from the ioscpm release.
Fixing it means either refreshing the images from romwbw_emu/disks and cutting a
new ioscpm release for the catalog to point at, or repinning DiskCatalog.cpp's
RELEASE_TAG - still v1.4.5 - at a release built from the current disks.  Three
documentation items below unwind when this lands, and so does the first checkbox
of the Store-build test plan.

- the core moved again while the images stood still.  v1.36 rebuilt both
utilities a second time (romwbw_emu docs/DOWNSTREAM_2026-08-25.md sections 4
and 5), so refreshing now brings more than the host path: W8 no longer truncates
a binary export at the first 1Ah byte - exporting w8.com itself produced 368
bytes of 1408 - both utilities accept a host path containing a space, their byte
counts are 32-bit rather than the low 16 bits, and both sources lost a bogus
`org 0100h` that had been padding w8.com with 256 leading zero bytes.  The old
R8 also has a destructive bug of its own that only the refresh fixes: an
unfiltered host basename makes an ambiguous FCB, and F_DELETE then erases every
matching CP/M file before creating the new one.

- upstream added romwbw_emu/disks/verify_disk_utils.sh (75ef2e8) for exactly
this drift - it checks that the R8/W8 inside the shipped images match their
source, and as of v1.36 it runs inside `make -C src test` and covers both
utilities rather than only w8.com.  Nothing under packaging/ runs it, or
anything like it, before a release.  Mind the diskdef if checking by hand:
hd1k_combo.img is wbw_hd1k_0 because of its 1 MB MBR prefix, a plain 8 MB image
is wbw_hd1k, and the wrong one lists garbage rather than failing.

Features the sibling ports have and this one does not
------------------------------------------------------

- the seven remote help topics have no bundled copy and no on-disk cache, so an
offline user - or a release whose assets were not attached - gets none of them.
HelpWindow.cpp ships two topics of its own (Getting Started, Configuration) and
caches the fetched ones in memory only, fifteen minutes, gone at restart.
ioscpm gained the offline fallback in its build 51 (4deea96), referencing
release_assets/ in place rather than copying it, which is the trick worth taking
too.  The order to mirror is download, then cache, then the copy shipped in the
binary.

- a mistyped config key is silently absorbed, and then silently deleted on the
next save.  cpmemu fixed the same class of thing in bb03afa; the two places here
are Config.cpp's from_json - every field is j.value(name, default) and to_json
writes only known names, so an unrecognised member is dropped at the next save -
and Keymap.h's KeyMap::build, which discards any name keyIdForName rejects with
`if (id >= 0)` and says nothing.  Note the "F1x" fix in CHANGELOG [Unreleased]
is a different thing: it made vkForName reject the typo instead of binding F1,
it did not make anything report it.
  Looked at on 2026-08-26 and deliberately not written blind.  The edit is not
the detection - collecting the member names json actually carries and
subtracting the ones from_json consumed is a dozen lines in one function - it is
that there is nowhere to put the answer.  Config.cpp has no window, no status
bar and no terminal; emu_error() reaches the log nobody reads.  The terminal is
the right place, and applyConfig() already prints there, so what this wants is
the same channel the ROM notice uses: collect during load, hand the text to
MainWindow and print it beside the ROM notice.  Note that channel does not
survive startEmulator() today - see the terminal-clear item below, which the
same design should fix at the same time.  That is a small design rather than a
one-line edit, and it wants a compiler.  The rejected-scrollback-binding item below is the same missing
channel seen from the other end - take the two at once.

- Reset reboots the machine with no confirmation - MainWindow::onEmulatorReset()
calls reset() straight away - and with "ctrlRToCpm": false a single Ctrl+R does
it.  Both mobile ports ask first.  A MessageBoxW version was written on
2026-08-26 and reverted unbuilt; if it is written again, note the choice it has
to make and that nothing here can test either way - both mobile ports ask
unconditionally, while asking only when isRunning() would spare the user a
dialog on a machine that is already stopped.

- the terminal bell is unconditional: TerminalView.cpp's 0x07 case calls
MessageBeep(MB_OK) with nothing to consult.  cpmdroid made it a setting.  A
config-file-only version of this was written on 2026-08-26 and reverted unbuilt

source files plus two documentation tables, which is small but is still four
files nothing here can compile.  Worth doing with the Settings work below rather
than on its own - the dialog needs a terminal section as much as a keyboard one,

- rebinding a key means closing the app and hand-editing JSON.  There is no

Small things a review of the sync round raised and did not take
---------------------------------------------------------------

None of these is a regression; each was measured and left deliberately.

- a 0-byte disk image is accepted and mounts as an empty disk rather than being
refused with an error: emu_io_windows.cpp's emu_file_load returns true for
size 0, EmulatorEngine::loadDisk passes it on, and HBIOSDispatch::loadDisk
range-checks the unit and nothing else.  NOT FIXABLE IN THIS REPO ALONE, which
is why it is still here: the shared emu_io_common.cc's emu_file_load does the
identical thing - measure_stream succeeds, resize(0) leaves an empty vector, the
fread is skipped for size 0 and it returns true - so a guard added here and
nowhere else makes this the one port that refuses a file the other three mount,
and divergence in the twelve hand-synced functions is the thing this port can
least afford.  Re-checked 2026-08-26 against romwbw_emu 657d61a: still true of
both.  It has to be taken in emu_io_common.cc first, with the ports following,
and the same change decides whether 0 bytes is refused in the backend or in
loadDisk - the backend is where the two trees have to agree.

- MainWindow::startEmulator() clears the terminal, which erases the two notices
applyConfig() prints when the saved ROM is unusable but loadDefaultROM() has
already put a good one in the banks - "NOTE: the saved ROM (...)" and "ERROR:
the saved ROM (X) was not found".  hasROM() is true for both, so the no-ROM
guard above the clear does not fire.  Pre-existing, and only visible when a ROM
has already failed to load.
  A fix was written on 2026-08-26 - keep the text in a member and reprint it
after the clear - and reverted, because review found it defective: the member
was cleared only at the top of applyConfig(), whose only callers are
loadSettings() and the profile load, so a user who read the notice, followed it
and picked a working ROM through onSelectROM() got the stale error reprinted at
them.  Whoever writes it again owns that lifetime: onSelectROM() succeeding has
to clear it, and so does anything else that makes the notice untrue.

- the four scrollback combinations (Shift+PageUp/PageDown, Ctrl+Home/End) are
intercepted at the top of TerminalView::handleKeyDown, before the
m_keymap.find() lookup a few lines below, so a config that binds them is
silently ignored rather than refused.  docs/CONFIGURATION.md now says which
four they are; making KeyMap::build reject them would be better still.  Left
alone on 2026-08-26 rather than written blind: dropping the binding is already
what happens, so "reject" is only worth writing once something can say so, and
that is the reporting channel the mistyped-config-key item above needs.  One
job, two ends.  KeyMap::build is header-only and rebuilds every binding the app
has, so it is not a function to edit without a compiler.
