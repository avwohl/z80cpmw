Needs a Windows machine
------------------------

- [WINDOWS] the Dazzler group in Settings is inert.  SettingsDialogWx's
loadSettings() and saveSettings() read and write m_settings.dazzlerEnabled,
dazzlerPort and dazzlerScale, but MainWindow::onEmulatorSettings seeds none of
them and reads none of them back, so the checkbox opens unchecked however the
machine is actually configured and anything set in it is discarded at OK.  The
real state lives in cfg.dazzlers[0], which only onViewDazzler touches.  Seeding
and writing back are two lines each; the question the fix has to answer first is
which of the two is authoritative when they disagree at startup.

- [WINDOWS] settings.debugMode is assigned false with a "TODO: get from
emulator" comment before the dialog opens and handed straight to
m_emulator->setDebug() after it, so the box always opens unticked and an OK from
someone who never touched it turns debug off.  Same function as the item above,
and the same shape of fault - a control with no seed - so take them together.

- [WINDOWS] the seven remote help topics can be bundled now, and the reason not
to has gone.  help_assets::resolveTopic already holds the order - download, then
cache, then the copy in the binary - and its third step is reached with an empty
bundled string, so this is one argument at one call site plus whatever carries
the bytes (RCDATA in z80cpmw.rc referencing ..\ioscpm\release_assets in place is
the shape that was scoped; verify rc.exe /i resolves a data file through an
include directory before writing eight lines of it, and note that it makes
..\ioscpm a THIRD required sibling checkout, which README.md's Requirements and
tests\run_tests.bat's guards would both have to say).  What blocked it was that
the topics were written for iOS, and that is fixed upstream rather than forked:
avwohl/ioscpm branch help-platform-neutral, "The shared help assets stop being
written for iOS only".  Bundling reads release_assets/ out of the sibling
checkout, so it gets the corrected text as soon as that branch is merged - a
NETWORKED reader still gets the old wording until those files are attached to a
GitHub release, which is ioscpm's own [RELEASE] item and not this port's to do.

- [WINDOWS] nothing calls help_assets::setCacheRoot(), so the help cache picks
its own directory.  HelpAssets.h says what the call should be -
EmulatorEngine::getUserDataDirectory() plus a help subdirectory - and until
MainWindow makes it, cacheDir builds the path out of %LOCALAPPDATA% from the
environment rather than through SHGetKnownFolderPath, which is what the other
three copies of that snippet do (getUserDataDirectory, DiskCatalog's
constructor, and getDataFolder in emu_io_windows.cpp).  One line, before the
first help window can open.

- [WINDOWS] help_topics::configurationMarkdown() carries an in-app copy of the
settings table that has drifted from the file it documents: there is no
display.bell row, and nothing tells the reader that keys can be bound from
Emulator > Settings > Keyboard rather than by hand.  It is a raw string literal
in HelpWindow.cpp and so needs a build to see, which is exactly how the File
Transfer topic outlived the same correction in README.md.

- [WINDOWS] a wrongly-typed section in z80cpmw.json is still lost to a later
save.  ConfigManager::load() suppresses the save it would have made itself,
which is a complete answer for a file that could not be read at all - the
quarantine has renamed it out from under every other save - but not for one that
parses with a section skipped by from_json's is_array()/is_object() guards.
Nothing quarantines that file, so the next explicit save writes our defaults
over text nobody read: MainWindow::saveWindowPlacement() at WM_CLOSE, the
first-run welcome flag, an NVRAM change.  Measured with "keyboard.keys" written
as an array - the user's binding was gone within twelve seconds of boot.  The
comment above partlyUnread in Config.cpp states both the gap and the fix: carry
the text we could not read through to the next to_json, which is a change to the
shape of the format rather than to its loader.

- [WINDOWS] ConfigManager::loadProfile() clears m_diagnostics before it can
fail, so loading a profile that will not parse takes down the report about
z80cpmw.json - settings which are still in force, since a failed profile load
changes nothing.  The clear was deliberately moved off the top of that function
so that asking for a profile which does not exist keeps the report; the same
reasoning applies one step further in.

- [WINDOWS] tests/test_render.cpp's "SGR 40-47 paint the whole cell" section
cannot fail for i == 0: ESC[40m sets a black background over a background that
is already black, so that one iteration asserts nothing.  The other seven carry
the section, so this is a hole in the evidence rather than a wrong result -
either give index 0 a non-black background to come back from, or skip it and say
why in the source.

- [WINDOWS] cpmemu has Windows work of its own - the rewritten console input
path, its test harness, and the cases its suite skips for want of the platform.
This project compiles none of that code.  See cpmemu/todo.txt, which owns it and
has the measurements.


Packaging and signing
----------------------

- [WINDOWS] [RELEASE] build-msix.ps1 -Beta: REHEARSE IT UNSIGNED, AND DO NOT
SIGN IT WHILE Version.h SAYS 1.0.22.  The rehearsal is what to run, and it runs:
build-msix.ps1 -Beta -SkipBuild -SkipSign exits 0, writes
dist\z80cpmw-1.0.22-beta-unsigned.msix and its .pdb, and leaves the published
dist\z80cpmw-1.0.22-beta.msix on hash 1549C223 before and after.  A SIGNED -Beta
run is forbidden until Version.h moves off 1.0.22, because v1.0.22-beta is
published and the script names its output from Version.h: such a run re-mints
the published artifact under its own name, and nothing in the script objects.
Assert-ExeVersion compares the exe against Version.h and says nothing about a
package being replaced, and the signing-kit guard does not fire because the kit
really is where it is expected to be.

  -WhatIf IS NOT A WAY TO FIND OUT, AND THAT IS WHY THIS ITEM IS WORDED SO HARD.
  Before dacdce5 the script had no [CmdletBinding()], so PowerShell collected
  -WhatIf into $args and the run proceeded for real.  That happened on
  2026-08-28, while checking that very premise: the run made a live Azure
  Trusted Signing call and re-minted the published 1.0.22 beta package from a
  different binary.  The GitHub release was never touched and the local copy was
  restored from it - its published digest 1549c223... matches dist\ again - but
  the signing call is spent.  -WhatIf is a hard binding error there now, and
  deliberately not SupportsShouldProcess.

  What is still owed: dist\ has no z80cpmw-1.0.22-beta.pdb and 1.0.22's symbols
  stay unrecoverable.  The -Beta branch copies bin\<Configuration>\z80cpmw.pdb
  out beside the .msix and errors out if it is not there, so a beta cannot ship
  symbol-less in silence again; the first signed -Beta run on a version that has
  not shipped is what proves that end to end, and 1.0.23 is where it happens.

- [WINDOWS] packaging/scripts/build-nsis.ps1 still has no [CmdletBinding()], so
a stray -WhatIf there is collected into $args and the run proceeds, exactly as
build-msix.ps1 did until dacdce5.  It is one line and its own commit;
STORE_SUBMISSION.md already names the gap.


The disk images are behind the core
------------------------------------

READ romwbw_emu/docs/RELEASE_ORDER_2026-08-25.md BEFORE PUBLISHING ANYTHING
HERE.  It owns the sequence and the two safety rules.  z80cpmw is step 3 of that
plan and is not a safety blocker.

- [RELEASE] the bundled images are stale, and the new
packaging/scripts/verify-disk-assets.sh now says so.  Measured 2026-08-27 on the
images unpacked from the published z80cpmw-1.0.22-beta.msix, which is how they
can be got at from a machine with no Windows build: hd1k_combo.img holds a
1079-byte r8.com where romwbw_emu/src/r8.asm now builds 1792, and a w8.com
carrying neither [hostpath] in its usage line nor the capability probe;
hd1k_games.img holds NEITHER UTILITY AT ALL, so no host file transfer works from
the games disk.  The stale R8 is the
half with teeth - an unfiltered host basename makes an ambiguous FCB and
F_DELETE then erases every matching CP/M file - so that destructive bug is live
in what ships today, not only in an old lineage.  Refreshing from
romwbw_emu/disks also brings the v1.36 rebuild: W8 no longer truncates a binary
export at the first 1Ah, both utilities accept a host path containing a space,
their byte counts are 32-bit rather than the low 16 bits, and both lost a bogus
org 0100h that had been padding w8.com with 256 leading zero bytes.  Landing it
means either cutting a new ioscpm release for the catalog to point at, or
repinning DiskCatalog.cpp's RELEASE_TAG - still v1.4.5 - at a release built from
the current disks.  Then run verify-disk-assets.sh over the staged disks;
STORE_SUBMISSION.md step 3 is where it sits in the flow.

- [RELEASE] several documents go the other way when the images are refreshed,
and not before.  docs/FILE_TRANSFER.md's "does not take one yet" paragraphs and
the step 0/1 caveats in its checklist come out; README.md's "W8 does not take a
host path yet" paragraph and the two cautions under it come out with them;
HelpWindow.cpp's "File Transfer (R8 / W8)" topic now carries the same three
blocks, each with its own deletion condition in a comment above the literal -

this before verify-disk-assets.sh passes on the staged images.
