Packaging and signing
----------------------

- [WINDOWS] STANDING RULE, not a task: NEVER MAKE A SIGNED build-msix.ps1 -Beta
RUN ON A VERSION THAT IS ALREADY PUBLISHED.  The script names its output from
Version.h, so such a run re-mints the published artifact under its own name and
nothing in the script objects - Assert-ExeVersion compares the exe against
Version.h and says nothing about a package being replaced, and the signing-kit
guard does not fire because the kit really is where it is expected to be.  It
has happened once, on 2026-08-28 against the published 1.0.22, and cost a live
Azure Trusted Signing call.  -WhatIf is a hard binding error there and is
deliberately not SupportsShouldProcess, so it is not a way to find out either;
the safe rehearsal is -Beta -SkipBuild -SkipSign, which writes a distinct
"-unsigned" name and reaches neither sign.ps1 nor the network.
  Check `gh release list` against Version.h before signing.  This belongs in
  KNOWN_PROBLEMS.md rather than here once somebody moves it - it can never be
  "done".

  The .pdb half of this item is CLOSED, in 1.0.23.  The signed run was made on
  2026-09-03, printed "Symbols kept", and dist\z80cpmw-1.0.23-beta.pdb is
  byte-identical to bin\Release\z80cpmw.pdb.  1.0.22's own symbols remain
  unrecoverable and always will be; that is a fact now, not a task.


The disk images are behind the core
------------------------------------

READ romwbw_emu/docs/RELEASE_ORDER_2026-08-25.md BEFORE PUBLISHING ANYTHING
HERE.  It owns the sequence and the two safety rules.  z80cpmw is step 3 of that
plan (code done, not a safety blocker) and step 5 (bump this port's catalog pin).

- [RELEASE] THE REFRESHED IMAGES NOW EXIST AND THIS IS A SMALLER JOB THAN IT
WAS.  Step 4 of the release order was done on 2026-09-01: ioscpm v1.4.12, 29
assets, published as a PRERELEASE so releases/latest still points at v1.4.11 and
no installed client of any port sees a change.  Measured here 2026-09-03: the
v1.4.5 and v1.4.12 disks.xml are 7042 bytes each and differ on ONE LINE, the
<sha256> of hd1k_combo.img (be19984e... -> 89b8ae1a...).  Every other filename,
size and hash is identical and so is the version attribute.  So:

  THE WHOLE JOB IS ONE LINE: repin RELEASE_TAG in DiskCatalog.cpp from v1.4.5
  to v1.4.12.  It is the single source of both catalog URLs, and the comment
  above it says what the pin is for.  Nothing else about the disk set moves, so
  the HBIOS/CBIOS pairing the pin protects is unchanged.

  There is nothing to restage.  1.0.23 ships no disk images at all - every port
  gets them from the ioscpm release area, which is the design - so the image a
  user runs is chosen entirely by RELEASE_TAG.  The bundled copies that used to
  ride in the package were never read by anything and are gone; see the
  packaging entry in CHANGELOG.md for how that was established.

  verify-disk-assets.sh is no longer a gate on this repo's package, because the
  package has no images in it.  It is still the right tool for checking a set of
  images before they are published, and it CANNOT RUN ON THIS MACHINE: cpmls is
  not on PATH and it exits 2 rather than guessing.  Upstream's own
  verify_disk_utils.sh passed on the exact v1.4.12 bytes, which is the assurance
  this repin rests on.

  Why it is worth doing: the stale R8 is the half with teeth.  An unfiltered
  host basename makes an ambiguous FCB and F_DELETE then erases every matching
  CP/M file, and v1.4.5 is what the catalog still serves, so that destructive
  bug reaches any user who downloads the combo disk today.  The refresh also
  brings the v1.36 rebuild - W8 no longer truncates a binary export at the first
  1Ah, both utilities accept a host path containing a space, their byte counts
  are 32-bit rather than the low 16 bits, and both lost a bogus org 0100h that
  had been padding w8.com with 256 leading zero bytes.

  Two gates that ARE cleared, so nobody re-derives them:
  - Step 5's sanitiser rule.  This backend is fopen-based, honours absolute
    paths deliberately and deletes nothing, which is why emu_host_path_caps()
    returns EMU_HOST_CAP_SAFE_PATHS honestly.  Already in the tree.
  - Step 5's second data-loss path, the catalog-version invalidation wipe.  It
    does not exist on this port: DiskCatalog.cpp never reads disks.xml's version
    attribute at all, and its only deletes are two partial-download cleanups and
    deleteDownloadedDisk() at the user's request.  The release order asks for
    this check per port and this is it.  (v1.4.12 did not move the attribute
    either, so it would not have fired even on a port that had the wipe.)

- [RELEASE] several documents go the other way when the images are refreshed,

- [WINDOWS] loadDefaultDisks() has no caller, and finding that out is what
established the bundled images were dead weight.  It looks for cpm_wbw.img and
zsys_wbw.img under the install directory's disks\ folder; grep the tree and the
