- 1.0.25 makes a superseded disk image visible and does not yet make it go away.
Two pieces are missing, and CHANGELOG [1.0.25] has the design behind both:

  * Nothing calls downloadDisk() for a DiskRefreshPlan::RefreshNow.  The caller
  has to be the UI rather than DiskCatalog, because isMounted is MainWindow's
  fact - replacing a file the running machine holds in a slot undoes itself on
  the next flush.  Wants an Update button beside Download and Delete.

    THE URL SWITCH HAS LANDED, SO THIS IS NOW LIVE RATHER THAN HYPOTHETICAL.
    The v0 catalog gives hd1k_combo the hash 0ca4ec60... where v1.4.12 gives it
    89b8ae1a..., which would have made every migrated combo read
    SupersededPristine - action() turns that into RefreshAutomatically and
    plan() into RefreshNow - had the equivalence below not been recorded first.
    Nothing calls either:
    grepping the tree, action, plan, RefreshNow, RefreshAutomatically and
    allowsUserRequestedUpdate appear only in DiskLedger and in
    tests\test_diskledger.cpp.  That wiring is what an Update button would
    supply.

    DECIDED 2026-09-05, AND THE VERDICT IS NO LONGER SUPERSEDED.  The two images
    were compared byte for byte: both 51,380,224 bytes, slices 1-5 identical,
    slice 0's directory listing the same 94 files, and all 94 extracting
    byte-identical - r8.com and w8.com included.  The 2,342 bytes that differ are
    CP/M slack between those files.  diskv0::isEquivalentPriorImage records that
    one pair and DiskLedger::freshness now returns Current for it, so the
    Settings column no longer says "Update available" and an Update button, when
    one is wired, will not offer 49 MB for nothing.  It is keyed on provenance:
    a download records the catalog it was fetched against, so only the migration
    can produce it, and it stops applying once this machine fetches the canonical
    image.  romwbw_disks docs/FINDINGS.md section 10 has the byte ranges.

  * A user who never opens Settings is never told.
  downloadAndStartWithDefaults() now fetches the catalog when it has to download
  something, but not when both default images are already there - which is the
  case this item is about - so a boot notice still means a network fetch at
  every launch: a real behaviour change, to decide rather than assume.

  MainWindow.cpp and SettingsDialogWx.cpp are in no suite and cannot be, so both
  are verified by driving the built app.  See WIP.md.

- The ROM gate cannot be checked by any suite, and the offline case it costs is
open.  romReadyToStart() and everything under it live in MainWindow.cpp, which
needs a real window and is in no suite; MANUAL_CHECKS.md "The ROM gate" is the
whole of the verification and none of it has been run.

  The open behaviour, not a defect: a machine set to a release other than the
  bundled one cannot start with no network even when that release's ROM is
  already in its data folder, because the published size and sha256 exist only in
  the catalog and this build will not load a ROM it cannot check.  The offer that
  follows the failed lookup gives the user a machine that boots, on the bundled
  release.  Doing better means remembering a ROM's published hash locally - a
  second provenance store beside DiskLedger's, keyed on a filename the config
  would also have to carry - and that is a design, not a tweak.

  Two smaller things the gate left behind.  The two bundled ROM names are still
  written out by hand in seven places that must move together: MainWindow.cpp's
  onSelectROM (menu id -> filename), the Settings write-back (filename -> menu
  id), loadDefaultROM (emu_avw.rom outright), loadPackagedRom (the same choice
  again), applyConfig (filename -> check mark), updateConfigFromState (id ->
  filename) and bundledRomwbwRelease (:2125-2127, which the gate itself added -
  three more emu_avw.rom paths, and deliberately not routed through
  findResourceFile), plus SettingsDialogWx::populateROMList's two labels.  And
  roms\emu_avw.rom and roms\emu_romwbw.rom are byte-identical to each other and
  to the catalog's emu_avw-v0-3.5.1.rom (all three 4b11402a... as of
  2026-09-06, c7abc580... before the HB_BNKCALL fix), so the second
  menu entry is a second name for the same 512 KB.

  The ROM refresh missed the suite.  tests\test_catalogv0.cpp's 3.5.1 fixture
  (:206) still publishes emu_avw as c7abc580, and the check at :521-523 reads
  "and the hash the bundled roms/emu_avw.rom already has", which stopped being
  true on 2026-09-06.  All 130 checks still pass, because the fixture is
  self-contained and nothing compares it to anything real - so the suite now
  asserts a hash no catalog serves, against a bundled ROM that does not have it.

scaffolding that let the storage migration rename the images in a release whose
catalog still called them hd1k_combo.img; the catalog now serves the v0 names and
v0NameFor() refuses those, so it is the identity function for every filename that
reaches it from a catalog entry.  Its five call sites - DiskCatalog.cpp:682

(deleteDownloadedDisk's removeRecord), :832 (getDiskPath), :1351

one line shorter.  Leave it until a release that can be built and driven: the one caller
that can still hand it a bare pre-v0 name is MainWindow's Settings write-back,
against a configuration whose rename did not complete, and that path is in no
suite.
