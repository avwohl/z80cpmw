Needs a Windows machine
------------------------

- [WINDOWS] THREE CHANGES IN THIS TREE HAVE NEVER BEEN COMPILED WITH MSVC.  (a)
emu_host_file_get_read_name() in emu_io_windows.cpp, written 2026-08-27 because
romwbw_emu made it a required backend function and hbios_dispatch.cc - which
this project compiles straight out of the sibling checkout - calls it
unconditionally, so the tree does not link without it.  The added statements
were type-checked in a clang shim, which is not a build.  (b) the 24
-ErrorAction Continue additions in build-msix.ps1 and build-nsis.ps1, which
nothing on this machine can even parse.  (c) ansiToCGAColor() in
TerminalView.cpp, and the expectations it moved in test_vt52.cpp.  (c) carries
more evidence than (a) does: the real TerminalView.cpp was compiled on a Mac
against a stubbed windows.h - the parser touches no Win32 - and the conformance
suite was run against it, 268 checks passing, and run again with the mapping
backed out, 36 failing with exactly the old expectations.  What it still wants
is a person looking at a real screen and agreeing that ESC[31m is red.  The
first Windows build settles (a) and (c) both: they either compile or they do
not, and run_tests.bat says the rest.

- [WINDOWS] there is no per-cell attribute beyond the packed CGA byte.  struct
TerminalCell carries a character, a foreground and a background and nothing
else, and the paint path selects a single m_font outside the row/column loop, so
bold / underline / blink / reverse have nowhere to live and nothing to render
them.  The gap is a flags byte plus a multi-HFONT paint path - roughly a day,
splitting cleanly into a parser commit and a rendering commit.  The conformance
suite is in the repository, so a regression in the rest would be caught.

- [WINDOWS] the seven remote help topics have no bundled copy and no on-disk
cache, so an offline user - or a release whose assets were not attached - gets
none of them.  HelpWindow.cpp ships two of its own and isLocalTopic() names only
those two; the fetched ones are cached in memory for fifteen minutes and are
gone at restart.  ioscpm gained the fallback in its build 51 (4deea96) by
referencing release_assets/ in place rather than copying it, which is the trick
worth taking.  The order to mirror is download, then cache, then the copy
shipped in the binary.

- [WINDOWS] a mistyped config key is silently absorbed, and then silently
deleted at the next save.  Config.cpp's from_json reads every field as
j.value(name, default) and to_json writes only known names, so an unrecognised
member is read by nobody and gone at the next save; Keymap.h's KeyMap::build
discards any name keyIdForName rejects and says nothing.  Detection is a dozen
lines - subtract the names from_json consumed from the members the json actually
carries.  The work is that there is nowhere to put the answer: Config.cpp has no
window, no status bar and no terminal, and emu_error() reaches a log nobody
reads.  applyConfig() already prints to the terminal, so the design is to
collect during load and hand the text to MainWindow, on the same channel the ROM
notice uses - a channel that does not survive startEmulator() today.  These next
two items are the same job seen from its other two ends; take all three at once.

- [WINDOWS] MainWindow::startEmulator() clears the terminal, which erases the
two notices applyConfig() prints when the saved ROM is unusable but
loadDefaultROM() has already put a good one in the banks.  hasROM() is true for
both, so the no-ROM guard above the clear does not fire.  Whoever writes this
owns the notice's lifetime: onSelectROM() succeeding has to clear it, and so
does anything else that makes the notice untrue.

- [WINDOWS] the four scrollback combinations (Shift+PageUp/PageDown,
Ctrl+Home/End) are intercepted at the top of TerminalView::handleKeyDown, before
the m_keymap.find() lookup below it, so a config that binds them is silently
ignored rather than refused.  docs/CONFIGURATION.md now says which four they
are; making KeyMap::build refuse them wants the reporting channel above.

- [WINDOWS] Reset reboots the machine with no confirmation -
MainWindow::onEmulatorReset() clears the terminal and calls reset() with no
guard - and with "ctrlRToCpm": false a single Ctrl+R does it.  Both mobile ports
ask first.  Note the choice, which nothing here can test either way: they ask
unconditionally, while asking only when isRunning() would spare the user a
dialog on a machine that is already stopped.

- [WINDOWS] the terminal bell is unconditional: TerminalView.cpp's 0x07 case
calls MessageBeep(MB_OK) with nothing to consult.  cpmdroid made it a setting.
Worth doing with the Settings item below rather than on its own - the dialog
needs a terminal section as much as a keyboard one, and a checkbox is the
discoverable half.

- [WINDOWS] rebinding a key means closing the app and hand-editing JSON.  There
is no keyboard section in Settings - SettingsDialogWx has ROM, disks, debug, the
manifest warning, scrollback, Dazzler and the catalog, and nothing else.  Worth
more now that the key map understands modifiers and so has more to say.

- [WINDOWS] build-msix.ps1's -Beta branch copies bin\<Configuration>\z80cpmw.pdb
out to dist\z80cpmw-<ver>-beta.pdb after signing and errors out if it is not
there, so a future beta cannot ship symbol-less in silence the way 1.0.22 did.
NEVER RUN - not once, not even -WhatIf.  Run build-msix.ps1 -Beta and confirm
the .pdb lands in dist\ beside the .msix.

- [WINDOWS] cpmemu has Windows work of its own - the rewritten console input
path, its test harness, and the cases its suite skips for want of the platform.
This project compiles none of that code.  See cpmemu/todo.txt, which owns it and
has the measurements.


The disk images are behind the core
------------------------------------

READ romwbw_emu/docs/RELEASE_ORDER_2026-08-25.md BEFORE PUBLISHING ANYTHING
HERE.  It owns the sequence and the two safety rules.  z80cpmw is step 3 of that
plan and is not a safety blocker.

- [RELEASE] the bundled images are stale, and the new
packaging/scripts/verify-disk-assets.sh now says so.  Measured 2026-08-27 on the
images unpacked from the published z80cpmw-1.0.22-beta.msix, which is how they
can be got at from a machine with no Windows build: hd1k_combo.img holds a
1079-byte r8.com where romwbw_emu/src/r8.asm now builds 1792, and a w8.com
carrying neither [hostpath] in its usage line nor the capability probe;
hd1k_games.img holds NEITHER UTILITY AT ALL, so no host file transfer works from
the games disk.  The stale R8 is the
half with teeth - an unfiltered host basename makes an ambiguous FCB and
F_DELETE then erases every matching CP/M file - so that destructive bug is live
in what ships today, not only in an old lineage.  Refreshing from
romwbw_emu/disks also brings the v1.36 rebuild: W8 no longer truncates a binary
export at the first 1Ah, both utilities accept a host path containing a space,
their byte counts are 32-bit rather than the low 16 bits, and both lost a bogus
org 0100h that had been padding w8.com with 256 leading zero bytes.  Landing it
means either cutting a new ioscpm release for the catalog to point at, or
repinning DiskCatalog.cpp's RELEASE_TAG - still v1.4.5 - at a release built from
the current disks.  Then run verify-disk-assets.sh over the staged disks;
STORE_SUBMISSION.md step 3 is where it sits in the flow.

- [WINDOWS] HelpWindow.cpp's "File Transfer (R8 / W8)" topic lists R8 and W8
together and then says "Give a full path (recommended)", so it reads as
endorsing both, and W8 takes no host path from the bundled images.  It is a
string in a .cpp, so it needs a build to see.  README.md carried the same claim
and no longer does.

- [RELEASE] several documents go the other way when the images are refreshed,
and not before.  docs/FILE_TRANSFER.md's "does not take one yet" paragraphs and
the step 0/1 caveats in its checklist come out; README.md's "W8 does not take a
host path yet" paragraph and the two cautions under it come out with them; and
MANUAL_CHECKS.md's struck-out W8 check is re-instated.  Do not do any of this
before verify-disk-assets.sh passes on the staged images.
