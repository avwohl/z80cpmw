Needs a Windows machine
------------------------

- [WINDOWS] DazzlerWindow::setScale sizes the window from the card's CURRENT
video mode - updateSize() uses m_dazzler->getWidth() * m_scale, which is 32 on a
fresh card - while DazzlerWindow::create() uses a fixed 128 * scale and says why
in a comment: "Fixed size for maximum resolution (128x128 in X4 2K mode).
Smaller modes will be scaled to fill this space", and paint() StretchBlt's the
mode over the whole client rect.  So setScale shrinks a window create() sized
correctly.  It now has NO caller: MainWindow::applyDazzlerState rebuilds through
create() instead, and says there that this block collapses back to one setScale
call once the function sizes from Dazzler::MAX_WIDTH.  Fix it that way or delete
it; leaving a function whose only behaviour is wrong is the third option and the
worst one.

- [WINDOWS] closing the Dazzler window does not tell MainWindow.  DazzlerWindow
answers WM_CLOSE with show(false) under the comment "Hide instead of destroy -
let main window manage lifetime", and nothing notifies the owner, so
m_dazzlerEnabled stays true and View > Dazzler stays ticked over a window that
is not on screen.  Reopening it costs two clicks, off and on again.  The fix is
a notification from DazzlerWindow's WM_CLOSE; applyDazzlerState already reads
the window's real visibility, so it needs the message rather than a new rule.

- [WINDOWS] MainWindow::applyConfig() carries its own copy of the Dazzler
create-and-show code, and it is the copy that did not get fixed: it does not
rebuild for a scale change, it does not re-port an existing card (enableDazzler
returns early when one exists), and it still show(true)s unconditionally, so
loading a profile reopens a Dazzler window the user had closed.  Routing it
through applyDazzlerState() fixes all three at once, which is why that function
was written as a function.

- [WINDOWS] docs/CONFIGURATION.md's "Wrong kind of value" bullet is now true of
only one case out of two.  It says "the next save of any kind writes the
built-in defaults over the section that was skipped ... Simply quitting the app
is enough to lose the section".  A section skipped in a file that otherwise READ
is carried through saves now and is safe; the sentence survives only for a file
that is both wrongly typed AND unreadable, where the carry is deliberately
dropped because the file has been quarantined.  The bullet does not distinguish
them, and it does not say that a carry goes back only to the file it came from,
so a user who saves a profile out of a config with a skipped section gets a
different file from the one the bullet leads them to expect.

- [WINDOWS] MANUAL_CHECKS.md's "keys as an array" step stops at "the block on
screen is the only warning the user gets".  It is now worth two more lines,
because both are behaviours that a regression would silently take away: the
block is still there after pressing OK in Settings, and still there after a
restart.

- [WINDOWS] DiskCatalog::m_downloadDir is the one member with no lock and no
argument written down for why it does not need one.  setDownloadDirectory()
writes it once, from loadSettings() at startup, and both workers plus
getDownloadDirectory() read it unsynchronised.  It is not a live bug today - no
worker can exist at the moment it is written - but that is a property of the
call order rather than of the class, and the class is the thing that grew a
documented threading contract when the two use-after-frees were closed.  Either
write the argument down beside it or give it the same treatment as the rest.

- [WINDOWS] cpmemu has Windows work of its own - the rewritten console input
path, its test harness, and the cases its suite skips for want of the platform.
This project compiles none of that code.  See cpmemu/todo.txt, which owns it and
has the measurements.


Packaging and signing
----------------------

- [WINDOWS] [RELEASE] build-msix.ps1 -Beta: REHEARSE IT UNSIGNED, AND DO NOT
SIGN IT WHILE Version.h SAYS 1.0.22.  The rehearsal is what to run, and it runs:
build-msix.ps1 -Beta -SkipBuild -SkipSign exits 0, writes
dist\z80cpmw-1.0.22-beta-unsigned.msix and its .pdb, and leaves the published
dist\z80cpmw-1.0.22-beta.msix on hash 1549C223 before and after.  A SIGNED -Beta
run is forbidden until Version.h moves off 1.0.22, because v1.0.22-beta is
published and the script names its output from Version.h: such a run re-mints
the published artifact under its own name, and nothing in the script objects.
Assert-ExeVersion compares the exe against Version.h and says nothing about a
package being replaced, and the signing-kit guard does not fire because the kit
really is where it is expected to be.

  -WhatIf IS NOT A WAY TO FIND OUT, AND THAT IS WHY THIS ITEM IS WORDED SO HARD.
  Before dacdce5 the script had no [CmdletBinding()], so PowerShell collected
  -WhatIf into $args and the run proceeded for real.  That happened on
  2026-08-28, while checking that very premise: the run made a live Azure
  Trusted Signing call and re-minted the published 1.0.22 beta package from a
  different binary.  The GitHub release was never touched and the local copy was
  restored from it - its published digest 1549c223... matches dist\ again - but
  the signing call is spent.  -WhatIf is a hard binding error there now, and
  deliberately not SupportsShouldProcess.

  What is still owed: dist\ has no z80cpmw-1.0.22-beta.pdb and 1.0.22's symbols
  stay unrecoverable.  The -Beta branch copies bin\<Configuration>\z80cpmw.pdb
  out beside the .msix and errors out if it is not there, so a beta cannot ship
  symbol-less in silence again; the first signed -Beta run on a version that has
  not shipped is what proves that end to end, and 1.0.23 is where it happens.

The parity document describes ports it has not read
---------------------------------------------------

- [DECISION] FEATURE_PARITY.md's row 2 and row 3 were corrected on 2026-09-02
after all three ports were read side by side for the first time.  What that
turned up is the reason this section exists rather than being three closed items:
the "Verified Android behaviour (2026-08-07)" block cited nine symbols that exist
nowhere in cpmdroid, in its tree or anywhere in its history - scrollbackLinesEdit,
applyTerminalSettings, sendBytes, replyListener, userScrollUp++, snapToLive,
resetTerminal, historyIsContiguous and visibleHistorySize - and four of the claims
they carried asserted the opposite of what that code does.  The correction then had
to be corrected in turn: the first pass called cpmdroid's keeping of history across a
cold boot a defect, when clear() documents it as a considered product decision, and
it repeated the old block's misattribution of the capture choke point.  Reading a
port from outside is harder than it looks even when you know that is the failure.  Meanwhile ioscpm's
row 2 had been a bare unqualified tick since 2026-07-25 over a feature that had
never captured a single line, and its row 3 was a tick over a port with no text
selection at all.  Neither was caught because the cells were filled in from commit
messages: row 2 was flipped in d630619 twelve minutes after ioscpm's b703acf
landed, without that repository's source being opened.  The decision to make is
whether a tick is allowed to mean anything other than "somebody read this port's
code and can name the symbol".

- [DECISION] check-sibling-drift.sh measures one thing, commits behind origin,
and that is why none of the above was visible to it.  Two additions are drafted
and neither is written: a shipped-build field in the sibling-readings block, so a
tick citing a build newer than what users can install says so; and a rule that an
item body asserting behaviour about a sibling must cite at least one symbol that
git grep resolves in that sibling at the recorded sha.  The second alone would
have caught all nine inventions above.  Both are edits here, and both want a
decision about how hard they should fail before they are worth writing.
